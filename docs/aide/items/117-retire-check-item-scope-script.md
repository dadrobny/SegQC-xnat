# Item 117 — Retire `scripts/check_item_scope.py` in favour of `aide scope`

> **Created:** 2026-08-19 · status tracked in [`progress.md`](../progress.md)
> **Stage:** none — loop-infrastructure maintenance, no roadmap stage (see Assumptions)
> **Queue:** none — authored outside the queue, riding the framework-update PR (see Assumptions)
> **Objectives:** G7
> **Suggested branch:** `chore/framework-1.14.0` (already checked out; this item rides that PR)

---

## Description

Delete this repo's `scripts/check_item_scope.py` and move its one live consumer
— the `scope-check` job in `.github/workflows/ci.yml` — onto the framework verb
`python .aide/scripts/aide.py scope`, which supersedes it.

Item 107 (Stage 26, deliverable D9) retired the `_PRE_NNN_*` byte-hash "scope
fences" and, in their place, built `scripts/check_item_scope.py` to assert the
*diff-time* claim directly: "this branch changed only the files its spec
declares." Item 107's own Decisions log recorded the intended end state — *"the
eventual home for this check is the framework (`aide-loop`), where it belongs to
every consumer rather than to this repo. Prototyping it here first is
deliberate."* Engine **1.7.0** did exactly that, promoting the idea into
`aide scope` and citing this repo by name: the script did framework-shaped work
— enforcing a framework convention, on framework documents, in the framework's
own loop — while living in the project. Engine 1.14.0 is now installed here. The
project copy is redundant, and keeping two implementations of one convention
means a fix landing upstream silently does not apply to the job that actually
gates this repo's PRs.

**In scope.** Deleting the script; retargeting the CI job at the verb; splitting
`tests/test_107_item_scope_check.py` (the half that tested the *script* goes,
the half that asserts item 107's *fence retirement* stays); retargeting
`tests/test_115_stage26_validation.py`'s AC9 block at the framework parser;
correcting `CLAUDE.md` and the two `insights.md` entries that describe the
script; a small parity test proving the surviving checker still emits the
signal.

**Not in scope.** Any change under `src/segfacet/**` — this item touches no
production code. Any change to `.aide/**`, which is generated by the framework
installer and must never be hand-edited here (`aide scope`'s own unit suite
lives upstream in `.aide/scripts/tests/test_aide_scope.py` and is maintained
there). Any rewrite of the documents that name the script as **provenance** —
`docs/aide/items/{107,110,115,116}-*.md` and `docs/aide/queue/queue-016.md`
record what was true when they were written and must survive untouched; two of
item 107's surviving tests deliberately read them.

**The non-obvious hazard.** `tests/test_115_stage26_validation.py` `exec()`s
`scripts/check_item_scope.py` at **module import time** (lines 360-363) to reuse
its `_parse_authorised_paths` for item 115's AC9. Deleting the script without
retargeting that block does not fail four tests — it is a *collection error*
that takes the whole module out of the suite. AC13-AC15 exist for this.

## Assumptions

- **This item serves no roadmap stage, and adds no `progress.md` deliverable
  row.** It is a follow-on to Stage 26's deliverable D9 (item 107), and Stage 26
  is ✅ complete — adding a bullet there would roll the stage back to 🚧 and
  misreport a finished stage as reopened. Loop-infrastructure maintenance
  legitimately has no stage. This is a maintainer decision, recorded here so the
  validator does not "fix" the absence; **do not run `aide progress set 117`**
  and do not add a row.
- **There is no queue entry and no claim branch.** The maintainer authored this
  item directly onto `chore/framework-1.14.0`, which already carries four
  commits taking the AIDE framework from engine 1.5.0 to 1.14.0; item 117 rides
  along in that same PR. So: no `aide claim`, no `aide sync --item 117`, no
  `aide/117-…` branch. The item's own scope check therefore takes an explicit
  base — see Validation.
- **CI behaviour is preserved byte-for-byte by the swap.** Both implementations
  use an explicit `--base` verbatim when one is given (`_scope_base_ref`,
  `.aide/scripts/aide.py:2812-2832`, returns it unchanged), and the CI job always
  passes one. The `--base` default differs (`"main"` in the script; resolved
  `--base` > recorded branch base > `main_branch`, each derived answer preferring
  its `origin/` counterpart, in the verb) but CI never exercises a default. This
  is the fact that de-risks the whole item.
- **Exit codes are identical**: `0` in scope · `1` something outside it · `2`
  could not check. A missing or empty `## Authorised paths` section is `2` in
  both — never a silent pass.
- **Two behaviour deltas are accepted deliberately.**
  1. *The always-authorised set widens.* The script exempted
     `docs/aide/progress.md` and `docs/aide/insights.md`; the verb exempts those
     **plus the item's own spec** (`cmd_scope` appends `rel_spec`). That is a
     loosening, and a safe one — every spec already lists itself — but AC14's
     sweep is what confirms no current spec depended on the stricter behaviour.
  2. *Sub-list semantics.* Only **May change** authorises. A path declared under
     **Asserts against** that changed anyway is reported as its own distinct
     finding ("changed, but listed under 'Asserts against' as
     pinned-not-changed"), not as a plain unauthorised path.
- **No existing spec needs rewriting for the sub-list form.** Verified
  empirically: `python .aide/scripts/aide.py scope 116 --base main` read item
  116's 11 flat bullets and reported against them rather than exiting 2, so the
  flat legacy form parses as **May change** (`parse_authorised_paths`'s
  docstring states this explicitly). AC14 pins it for all ten queue-016 specs.
- **Recorded insights about the script are partly stale, and this item corrects
  the record rather than inheriting it.** `_path_matches`
  (`scripts/check_item_scope.py:137-152`) *does* support per-segment `fnmatch`,
  so `tests/corpus/golden/*.json` works; the open `insights.md` entry claiming
  it supports "only an exact path or a `/**` suffix" is out of date and is
  ticked accordingly (AC4). And the merge-base *is* used by both — the real
  defect was only the stale `--base main` **default**.
- **`aide scope` is stdlib-only**, so the CI job keeps its "no venv, no Docker,
  no network beyond the checkout" property. It needs `tomllib`, hence Python
  3.11+ (AC9); the current job relies on whatever `python` the runner image
  happens to provide, which AC9 makes explicit rather than incidental.
- **A project test may exercise the framework CLI.** `.aide/**` is generated and
  never hand-edited here, but `tests/test_114_documentation_corrections.py`
  already loads `.aide/scripts/aide.py` via `importlib` and calls `run_checks`.
  AC13/AC16/AC17 follow that established pattern. The coupling is deliberate and
  narrow: these assert only the contract the CI job depends on (exit codes, and
  that a violating path is named), never the verb's internals, which are covered
  upstream by `.aide/scripts/tests/test_aide_scope.py` — a suite this repo's
  `testpaths = ["tests"]` does **not** collect.
- **The `CLAUDE.md` edit is PR-gated, and that gate is already satisfied.**
  `CLAUDE.md` is a framework/process file that must land via a reviewed PR;
  riding `chore/framework-1.14.0` *is* that PR. Nothing here merges straight to
  `main`.

## Implementation Steps

The order matters: **the parity run happens while both checkers still exist**,
and the deletion is last.

1. **Run the parity comparison first, before touching anything.** On the current
   branch, pick one known-clean state and one known-violating state and run both
   checkers over each with the same explicit base:
   - clean: `python scripts/check_item_scope.py docs/aide/items/117-retire-check-item-scope-script.md --base b2fb55c`
     and `python .aide/scripts/aide.py scope 117 --base b2fb55c`
   - violating: commit a scratch edit to a file outside this item's **May
     change** list, re-run both, then revert the scratch commit.

   Record both exit codes and both reported-path sets for both states in this
   spec's Decisions log as the **Parity check** entry (AC18), together with any
   difference attributable to the two accepted deltas.
2. **Retarget the CI job** (`.github/workflows/ci.yml`, `scope-check`). Keep the
   job's shape, its `fetch-depth: 0`, and — critically — the **anchored** `sed`
   at line 47. Add an `actions/setup-python@v5` step pinned to `"3.11"`. The
   resolve step now yields a *number*, not a path, because the verb takes an
   item number:

   ```yaml
         - name: Resolve item number for this branch
           id: item
           env:
             HEAD_REF: ${{ github.head_ref }}
           run: |
             set -e
             item_number=$(echo "$HEAD_REF" | sed -n 's|^aide/\([0-9]\{3\}\)-.*|\1|p')
             if [ -z "$item_number" ]; then
               echo "could not extract a 3-digit item number from branch '$HEAD_REF'; skipping scope check"
               echo "item=" >> "$GITHUB_OUTPUT"
               exit 0
             fi
             echo "item=$item_number" >> "$GITHUB_OUTPUT"
         - name: Run scope check
           if: steps.item.outputs.item != ''
           run: |
             python .aide/scripts/aide.py scope "${{ steps.item.outputs.item }}" --base "origin/${{ github.base_ref }}"
   ```

   Two traps to record in the job's comment block, both of which cost a CI round
   trip if rediscovered:
   - **Do not drop the explicit number and rely on the verb's branch
     inference.** `actions/checkout` leaves a **detached HEAD** on
     `pull_request` events, so `_current_branch` gives the verb nothing to
     anchor on and it exits `2` — a red PR on every item.
   - **Keep the `^aide/[0-9]{3}-` anchoring.** An unanchored 3-digit match read
     `aide/queue-016` as item 016 and hard-errored on an unrelated spec; the
     anchored form correctly resolves a queue branch to nothing, and the job
     skips.

   Note the one intended difference: the old step also skipped when no
   `docs/aide/items/NNN-*.md` existed. That case now reaches the verb and exits
   `2` ("no spec for item NNN"). This is correct and deliberate — an `aide/NNN-`
   branch with no spec is a real defect, and exit 2 is the framework's
   "reported, never silently passed" contract.
3. **Split `tests/test_107_item_scope_check.py`.** Delete the 17 test functions
   from `test_ac5_script_exists_and_imports_only_stdlib` (line 127) through
   `test_adv_nonexistent_base_ref_is_a_clear_nonzero_error` (line ~414), plus
   the helpers and imports only they used (`_SCRIPT`, `_STDLIB_FALLBACK`,
   `_git`, `_init_repo`, `_write`, `_commit`, `_write_spec`, `_run_checker`;
   `ast`, `subprocess`, `sys`, `pytest`). Keep `_TESTS_DIR`, `_REPO_ROOT`,
   `_rel`, `_all_test_sources`, `_FENCE_ITEM_NUMBERS`, `_FENCE_PATTERN` and the
   `re` / `Path` imports — the surviving tests use them. **Keep the filename**;
   renaming the module loses the history that ties it to item 107. Rewrite the
   module docstring to say what it now covers.
4. **Retarget the two `test_ac11_ci_workflow_*` tests** in that module at the
   new command: the first must assert the workflow invokes
   `.aide/scripts/aide.py scope`; the second (`base_ref`) is already true of the
   new job and needs no change. Leave both names as they are — they still
   discharge item 107's AC11 ("CI runs the check on pull requests"), now against
   the current command.
5. **Retarget `tests/test_115_stage26_validation.py`'s AC9 block.** Replace the
   `_CHECKER_PATH` / `exec(compile(...))` block (lines 360-363) with an
   `importlib` load of `.aide/scripts/aide.py`, taking `parse_authorised_paths`
   and `declares_nothing` from it (the recipe test_114 already uses at lines
   498-500, and the upstream suite at `test_aide_scope.py:14-18`). Then adjust
   the four AC9 tests to the framework parser's return type — an
   `AuthorisedPaths` named tuple or `None`, not a list or `None`:
   - `test_ac9_spec_declares_nonempty_authorised_paths` → assert
     `not declares_nothing(parsed)`.
   - `test_ac9_checker_parses_spec_without_error` → assert the result is `None`
     or an `AuthorisedPaths`.
   - `test_ac9_all_ten_queue_016_items_covered` → unchanged.
   - `test_adv_authorised_paths_heading_with_no_bullets_is_distinguished_from_missing`
     → the heading-with-no-bullets case returns a present-but-empty
     `AuthorisedPaths([], [])`, not `None`; keep the distinction it was written
     to make.

   Item 115's AC9 *claim* is preserved exactly — only the parser behind it
   changes. Do not weaken or delete the block.
6. **Correct the five stale comment blocks** in
   `tests/test_{099,100,101,103,105}_*.py`, each of which reads "Diff-time scope
   is now checked by `scripts/check_item_scope.py` on the branch." Change the
   command named; **comment text only** — no assertion, import or test body in
   those five modules may change.
7. **Write `tests/test_117_scope_verb_swap.py`** (see Testing Strategy).
8. **Correct `CLAUDE.md`.** Remove the Gotchas bullet describing the script as
   superseded-but-present and its retirement as a future work item, and fix the
   CLI bullet's parenthetical (line ~196), which names the script and defers
   "see below" to that bullet. State the finished position plainly, or drop the
   parenthetical entirely if the CLI bullet already says enough.
9. **Tick the two `insights.md` entries** — the `_path_matches` one and the
   stale-`--base main` one — in place, append-only: a `→` pointer naming item
   117, with the `_path_matches` pointer also recording that the claim was
   already stale when ticked (the glob support existed). Never rewrite or delete
   the captured text.
10. **Delete `scripts/check_item_scope.py`** — last, after the parity run is
    recorded and every consumer has moved.
11. Run the full suite and `python .aide/scripts/aide.py check`; confirm green
    and no new warning.

## Decisions & Trade-offs

**Parity check (2026-08-19, before deletion).** Ran both checkers head-to-head
on `chore/framework-1.14.0` with the same explicit `--base b2fb55c`, before
`scripts/check_item_scope.py` was removed:

- **Clean state** (tree as committed at `655432f`, item 117's own changes only):
  - `python scripts/check_item_scope.py docs/aide/items/117-retire-check-item-scope-script.md --base b2fb55c`
    → **exit 1**, reporting all 10 changed files (including the spec itself)
    as "not authorised by docs/aide/items/117-retire-check-item-scope-script.md".
  - `python .aide/scripts/aide.py scope 117 --base b2fb55c` → **exit 0**,
    "OK (item 117, 10 changed file(s) all authorised, vs b2fb55c)".
  - **Divergence, and why it is expected**: the old script predates engine
    1.6.0's **May change** / **Asserts against** sub-list syntax that this
    spec's own `## Authorised paths` section uses. Its parser only understood
    flat bullets, so on this spec it parses zero authorised paths and reports
    every changed file — including the spec itself, since the old script never
    exempted the item's own spec — as a violation. This is exactly the two
    accepted deltas in combination: sub-list awareness, and the wider
    always-authorised set that includes the item's own spec.
- **Violating state**: committed a scratch one-line edit to `README.md` (a
  file outside item 117's **May change** list), re-ran both, then reverted the
  scratch commit with a forward commit (`git checkout <prior-commit> --
  README.md` + commit, not a history rewrite):
  - `python scripts/check_item_scope.py docs/aide/items/117-retire-check-item-scope-script.md --base b2fb55c`
    → **exit 1**, `README.md not authorised by docs/aide/items/117-retire-check-item-scope-script.md`
    (plus the same 10 false positives as the clean-state run above, for the
    same sub-list-unaware-parser reason).
  - `python .aide/scripts/aide.py scope 117 --base b2fb55c` → **exit 1**,
    `error: README.md not authorised by docs/aide/items/117-retire-check-item-scope-script.md`,
    `aide scope: FAIL (item 117, 1 of 11 changed file(s) outside scope, vs b2fb55c)`.
  - Both checkers correctly flag `README.md` by name in the violating state —
    the "still has teeth" property survives the swap.

**Conclusion**: the verb correctly authorises the clean state (exit 0) where
the script false-positives on the whole change set due to its sub-list
blindness, and both correctly reject the same out-of-scope file in the
violating state. The two accepted deltas from the Assumptions section — the
wider always-authorised set (the item's own spec) and sub-list awareness (May
change vs. Asserts against) — fully account for the clean-state divergence;
no unexplained behaviour difference was observed.
